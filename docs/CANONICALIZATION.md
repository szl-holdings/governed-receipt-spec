# Canonicalization profiles for SZL receipts (proposal)

Status: **decision recorded 2026-11-12 (owner-approved)**. This change touches no existing serializer and no existing digest.

## Problem (measured)
A differential run over five estate serializers, fed identical inputs (`conformance/canonicalization-v1.json`), produced up to three distinct byte strings for the same value. They disagree on:

- non-ASCII escaping
- integral floats (`1.0` vs `1`)
- `-0.0`
- exponent form (`1e-07` vs `1e-7`, `1e+16` vs `10000000000000000`)
- astral-plane key order (code point vs UTF-16)
- whether NaN and Infinity are refused

| Serializer | Repo | Bytes match profile |
|---|---|---|
| `szl_evidence_core.canonical.canonical_bytes` (default) | szl-evidence-core | `szl.canon/v1` |
| `szl_receipt._canonical.canonical_json` | szl-receipt | `szl.lambda/v1` |
| `khipu_consensus.canonical_json` | khipu-consensus | `szl.lambda/v1` for finite input. `main` still emits `NaN` and `Infinity` (fix in khipu-consensus#61). |
| `szl_receipts.jcs.jcs_canon_bytes` | szl-evidence-litellm | `rfc8785` |
| `szl_router.receipts.request_digest` | szl-router | `szl.canon/v1` for finite JSON. Request bodies are already parsed with non-finite numbers refused. |

None of these is wrong on its own terms. The defect is that a digest does not say which profile produced it, so the same receipt body verifies under one library and fails under another.

## Profiles
These are the three profiles already defined in `szl_evidence_core.canonical`. All three sort keys, use compact separators, and refuse NaN, Infinity and -Infinity.

- **`szl.canon/v1`**: Python `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=True, allow_nan=False)`.
- **`szl.lambda/v1`**: the same with `ensure_ascii=False`. This is the bytes pinned by the Λ contract.
- **`rfc8785`**: the RFC 8785 JSON Canonicalization Scheme. Numbers use ECMAScript `Number::toString`, `-0` serialises as `0`, keys sort by UTF-16 code units, and non-integral integers beyond the double range are refused.

Each profile row in the vectors is generated by `szl_evidence_core`. The `rfc8785` rows are cross-checked byte-for-byte against the independent `rfc8785` PyPI package. The one recorded difference is `2**53` exactly: the PyPI package refuses it because it is outside the JS safe-integer range, while `szl_evidence_core` accepts it because it is an exact double. The vectors mark that case `implementations_may_reject`.

## Proposal
1. **Freeze.** `szl.canon/v1` and `szl.lambda/v1` are frozen byte-for-byte. Existing receipts, chains, Λ verdicts and published digests keep verifying. No in-place switch of any existing serializer.
2. **Pin every copy.** Each estate copy carries a conformance test against these vectors for the profile it actually emits, so silent drift fails CI. Draft PRs: szl-receipt, szl-evidence-litellm, szl-evidence-core, and khipu-consensus#61.
3. **Name the profile.** New receipt versions should record the profile next to the digest (for example `"canon": "rfc8785"`), the way the algorithm is already recorded. A verifier then never guesses.
4. **Default for new formats: `rfc8785`.** It is the only profile with an RFC and independent implementations in other languages. It is adopted for *new* receipt versions only; see Decision below. Defining the first such receipt version is follow-up work.

## Decision (2026-11-12)
1. **RFC 8785 applies only to new receipt versions.** No existing receipt format, serializer or chain switches profile in place.
2. **Every new digest records its format.** A new receipt version stores the canonicalization profile next to each digest it carries, together with the algorithm. Example: `{"digest": "sha256:<hex>", "canon": "rfc8785"}`. The `canon` value is one of the profile ids in `conformance/canonicalization-v1.json`. A verifier MUST refuse a new-version digest with no `canon` field, and MUST NOT guess.
3. **Existing digests stay unchanged.** Receipts and chains already emitted under `szl.canon/v1` or `szl.lambda/v1`, Λ verdicts, and published or MEASURED digests keep their bytes and keep verifying with their original serializer. Records that carry no `canon` field are read as the legacy profile their emitting library already uses, as pinned by that library's conformance test.
4. **Existing serializers are frozen.** `szl_receipt._canonical.canonical_json`, `khipu_consensus.canonical_json`, `szl_receipts.jcs.jcs_canon_bytes`, `szl_evidence_core.canonical` and `szl_router.receipts.request_digest` are not changed by this decision. The only planned fix is khipu-consensus#61's refusal of NaN and Infinity, which never produced valid JSON.

## Out of scope / blocked
Moving `szl-receipt` or `khipu-consensus` to `rfc8785` in place would change digests of receipts that contain integral floats, `-0.0`, small or large exponents, or astral keys. Measured: swapping `szl-receipt` to JCS fails 41 of its tests, including `test_finite_bytes_digests_and_existing_signatures_stay_compatible` and Λ recompute checks. That would alter LIVE/MEASURED values, so it is not proposed here.
